# 网文推荐引擎（Recommendation Engine）

## 前置依赖（必须按序执行，不得跳过）

1. 加载 `novel-preference-profile`：读 `novel-data/preference-profile.yaml`。
   - **文件不存在**：先走偏好采集流程，不要凭常识猜口味。
2. 加载 `novel-reading-log`：读 `novel-data/reading-history.jsonl` 作为排除集。
3. 只有 1、2 都到位才进入检索。**"先搜后想"是本技能要消除的头号失败模式。**

## 流程

### 阶段 1：候选生成（宽进）

- 按偏好档案里的强标签（weight ≥ 4）组合检索，一次覆盖 2-4 个方向，不要只搜一个窄方向。
- 每个方向至少取 5 个候选，得到 20-40 本粗池。**宁可多，不要在此阶段过滤。**
- 候选必须记录来源 URL，来源是后续可信度的依据。

### 阶段 2：硬过滤（去噪）

按顺序剔除，任何一条命中即淘汰，不做"也许还行"的妥协：

1. **已读**：跑 `dedupe-check.mjs`，DUP 全部剔除（含别名命中）。
2. **硬雷点**：命中 `dealbreakers.hard` 的任何一条 → 剔除。
3. **平台/付费冲突**：用户只接受免费但书在付费站且无免费渠道 → 剔除或标注降级。
4. **更新状态冲突**：用户只要完本但书在连载 → 剔除（除非用户明确接受追更）。
5. **未核实**：搜不到可靠来源、书名作者对不上 → 剔除（宁可少推，不可推不存在的书）。

淘汰推理要能说清，用户问"为什么没有 X"时要能回答。

### 阶段 3：打分（精排）

对存活候选按 9 个维度打分。权重来自偏好档案，**不是固定值**；下面括号内是典型默认：

| 维度 | 说明 |
|---|---|
| 题材契合 | 与强标签的重合度（权重最高） |
| 核心爽点契合 | 用户要的"爽点结构"是否匹配（如升级流/智斗/日常） |
| 主角人设 | 性格、行事风格是否合口味（圣母/龙傲天/理智流差异极大） |
| 节奏 | 开局是否快、中后期是否注水 |
| 文笔 | 与用户容忍度匹配 |
| 独特性 | 是否有辨识度，而非套路复刻 |
| 完成度 | 完结/连载、是否烂尾口碑 |
| 平台适配 | 可及性、付费、阅读体验 |
| 雷点风险 | **减分项**，命中 soft 雷点的概率与严重度 |

打分要点：
- 分数是**相对该用户**的，不是作品绝对质量。公认神作但口味不合 = 低分。
- 每个分数必须有可追溯依据（来源 URL 或历史库证据），不允许凭印象给分。
- 最终只推 **3-5 本**。推 10 本等于把筛选工作推回给用户，是本技能要避免的懒惰。

> **⚠ 此条已被推翻（2026-09-30）**：用户明确要求每批 20 本起步。原规则的前提是"我能选出高命中的少数几本"，但历史数据显示该前提不成立（弃书率 68%，我推荐的书通过率极低）。筛选依据在试听前不可得，因此把量交给用户、把过滤交给我，是更有效的分工。详见阶段 4。

### 阶段 4：输出（候选池形态，2026-09-30 用户明确要求）

**每批至少 20 本起步。** 用户原话："我的建议是你下次推荐至少20本起步"。

该要求基于一条被数据验证的现实：**听感无法预测，只能靠试**。历史库统计显示用户弃书率 68%，此前"精选 3-5 本"的模式通过率极低——因为筛选依据（听感）在试听前不可得。用户对此的判断："就像你买hifi耳机，你最多只能知道这是什么单元，其他商家宣传所谓冷暖声女毒之类的很可能只是营销话术而已，不去听怎么可能知道"。

**因此本技能输出候选池，不输出精选书单：**

1. **禁止"为什么适合你"式论证**。禁止使用"宏大世界观""思想深刻""智性爽感""意识形态生成性"这类**不可证伪的评价词**——它们与"女毒"是同一物种的营销话术。我没有任何手段在用户试听前检验它们。
2. **每本只给可查硬事实**：书名、作者、完结状态、字数、平台、是否命中已知雷点特征。
3. **按雷点特征打标，而非按推荐度排序**——让用户 3 秒扫过即可排除。
4. **量优先于准**：宁可 20 本里 2 本可用，也不要 3 本里 0 本可用。用户试读成本低（几章即可判断），检索成本由我承担。

**输出格式（每本一行，字段固定）：**

```
书名 | 作者 | 完/连载 | 字数 | 平台 | 标记
```

标记只用于风险提示：`⚠太早`、`⚠乐子文门槛`、`⚠疑似缝合`、`⚠主角待核`、`⚠长`。无标记即干净候选。

### 硬过滤（进入候选池前必须剔除）

依据用户历史库 25 本 dropped 的实测分布（`writing_quality` 9 / `lost_interest` 6 / `protagonist_annoying` 5 / `pace_slow` 3）：

- 作者在 `avoid_confirmed` / `avoid` 名单 → 剔除
- 首发晋江文学城 → 剔除（平台级）
- 未完结（除非用户明确接受）→ 剔除或标注
- 命中「帝霸式小白文」三特征（无敌无代价 / 数值无缘无故膨胀 / 生造词堆砌设定）→ 剔除。**这是最大单一死因，且可从公开资料判断，必须查**
- 受害者三条件同时成立（永远受害 + 无道德瑕疵白莲花 + 身边人被害）→ 剔除
- 男主与男二暧昧激情线 → 剔除
- 女频 / 纯爱 / 后宫（美人相）→ 剔除

### 阶段 5：反馈闭环

用户给出反馈后（看了/没看/好看/弃了），必须回到 `novel-reading-log` 与 `novel-preference-profile` 更新，并说明"我据此调整了什么偏好"。**不做闭环的推荐会一直重复同样的错误。**

## 反面清单（不要做）

- 不要在没有偏好档案时开始推荐。
- 不要把 web_search 的摘要当作已核实事实——摘要会过时、会张冠李戴，关键信息（状态、字数、是否烂尾）要抓页面确认。
- 不要推荐用户历史库里已有的书（含别名、含系列前作）。
- 不要因为"这是经典/神作"就推荐口味不符的书。
- 不要只给好评不给缺点。
- 不要在用户明确说"只要完本"时推荐连载作品。
- **不要一次推少于 20 本**（2026-09-30 用户要求）。
- **不要写"为什么适合你"式论证或任何不可证伪的评价词**——用户已明确此类内容等同营销话术。

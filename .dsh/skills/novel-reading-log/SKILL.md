# 阅读历史库（Reading Log）

## 目标

维护 `novel-data/reading-history.jsonl`：一份**可机器去重、可反推口味**的阅读流水账。它同时服务两个目的——推荐时排除已读，以及为偏好档案提供证据。

## 为什么用 JSONL 而不是表格/YAML

- 追加一条记录 = 追加一行，不重写整个文件，避免编辑大文件时出错。
- 逐行 JSON 可被脚本直接消费（`scripts/` 下的工具按行解析）。
- 单行损坏不影响其余记录。

## 数据契约

每行一个 JSON 对象。字段定义与枚举值见 `assets/reading-history.schema.md`；新增字段必须先改 schema 文档再改数据。

**去重键**：`title` + `author` 的规范化形式（去空格、去书名号、去“（完结）”等后缀、简繁归一）。同一本书**只允许一行**，状态变化就改那一行，不要追加新行。

判断“是不是同一本书”时注意网文特有的坑：
- 同名书极多，必须带作者；作者也同名时用平台区分。
- 改名/别名（《A》曾用名《B》）记在 `aliases`，去重时一并比对，否则会把已读的书当新书推。
- 系列作品（第一部/第二部）视为不同条目，但记 `series` 字段以免推续作当新书。

## 状态机

`status` 取值与语义（不要在枚举外自由发挥）：

| status | 含义 | 必填字段 |
|---|---|---|
| `finished` | 已读完 | `rating` |
| `reading` | 在读 | `progress` |
| `dropped` | 弃书 | `drop_reason`（**最重要**）、`progress` |
| `plan` | 想看/待读 | — |
| `paused` | 暂停（非弃书，可能回坑） | `progress` |

`rating` 用 1-5 整数：5 = 会主动二刷；4 = 好看，愿意推给别人；3 = 还行，看完不亏；2 = 勉强看完；1 = 后悔看。**未读完的书不要打分**（用 `drop_reason` 表达），否则会污染口味推断。

## 操作流程

### 1. 批量导入历史书单

用户给一大段书单（可能带评分、平台、进度）时：

1. 逐条解析成 JSON 行，**先不要**写入。
2. 对书名做规范化，检查与本文件已有记录的重复（含 `aliases` 比对）。
3. 有歧义（同名、作者缺失、疑似系列）的条目**单独列出来问用户**，不要猜。
4. 确认后一次性追加写入，并向用户回报：新增 N 条、跳过重复 M 条、待确认 K 条。

### 2. 单条记录

用户说“我看了《X》，弃了，因为 Y”时，直接改/写该行，并把 Y 抽象成偏好（交 `novel-preference-profile` 处理）。

### 3. 推荐前去重

生成推荐前，读取全部 `title`/`aliases`/`author` 作为排除集，并额外排除：
- `series` 匹配但用户没读完前作的续作；
- 用户明确表示过“永不再看该作者”的作者。

### 4. 弃书原因结构化

`drop_reason` 不要写自由文本，用 `code` + `note`：

- `pace_slow` 节奏慢 / `pace_rushed` 后期赶
- `protagonist_annoying` 主角人设劝退
- `harem_nonsense` 感情线/后宫处理差
- `power_creep_bad` 战力崩坏、无敌流无聊
- `plot_logic` 逻辑硬伤
- `writing_quality` 文笔
- `translation_mt` 机翻感 / `ai_generated` 疑似 AI 水文
- `platform_issue` 平台体验（广告、烂尾锁章）
- `lost_interest` 单纯没兴趣（**注意**：这条对口味推断价值低，要追问具体原因）

同一个 `code` 出现 ≥ 3 次，就该升级为偏好档案里的雷点；这是历史库最重要的用途。

## 输出要求

操作后回报：文件路径、当前总记录数、按状态分布、本次变更明细。用户问“我读过什么”时，按 `rating` 倒序或按时间倒序给出可读列表，而不是打印 JSON。

## 反面清单（不要做）

- 不要为同一本书追加第二行（去重键必须遵守）。
- 不要给未读完的书打分。
- 不要把 `lost_interest` 直接当结论，它通常是其他原因的委婉说法。
- 不要在用户只是**提到**某本书（而非表示读过）时就入库；先确认。

# 网文偏好档案（Preference Profile）

## 目标

把用户零散的口语化描述（“我就爱看主角一路碾压”“受不了圣母”）转成**结构化、可打分、可迭代**的偏好模型，存到 `novel-data/preference-profile.yaml`。推荐质量的上限由这份档案决定，而不是由搜到多少本书决定。

## 数据契约

唯一权威文件：`novel-data/preference-profile.yaml`（首次使用时从 `assets/preference-profile.template.yaml` 复制）。
字段含义与取值范围以模板内注释为准；改字段结构时必须同步改模板，避免两份定义漂移。

核心设计原则：

1. **权重而非标签**：标签用 `weight: 1..5`。`5` = 决定性的、没有就不看；`1` = 有更好、没有也行。
2. **雷点独立成表**：雷点不用“负权重”表达，单独放 `dealbreakers`，并区分 `hard`（踩到直接弃书）与 `soft`（踩到会明显掉分）。
3. **偏好必须有证据**：每条偏好记录 `evidence`（来自哪本书、哪句反馈）。没有证据的偏好标 `confidence: low`，不得在推荐理由里当作硬条件引用。
4. **记录“为什么”**：用户弃书原因比评分信息量大得多，写进 `novel-reading-log` 后要回灌成偏好。

## 操作流程

### 1. 建档式采集（用户一次性给大量信息时）

用户给了长段自述或历史书单时，不要逐条追问。按下面顺序做：

1. 先通读，用 `novel-reading-log` 技能把提及的书**全部**入库。
2. 从书单里**反推**偏好（读了 10 本系统流 → 系统流是强偏好），标注 `confidence: inferred`。
3. 只针对**推不出来的关键维度**追问，一次问不超过 4 个问题，用选项形式而非开放式。
4. 把推断结果**显式回报**给用户确认（“我从你的书单推断出 A/B/C，其中 C 我不确定，对吗？”），确认后才把 `confidence` 提升为 `confirmed`。

### 2. 交互式采集（用户只给模糊方向时）

按“预算 6 问”推进，每问都要能直接改变推荐结果，问完即停：

| 顺序 | 维度 | 为什么必问 |
|---|---|---|
| 1 | 最近 3 本让你觉得“好看”的书 | 最快的口味锚点，比任何标签都准 |
| 2 | 最近 1-2 本弃书 + 弃书位置 | 定位雷点，尤其是“前 20 章弃”= 节奏问题 |
| 3 | 男频/女频、偏好平台、是否接受付费 | 决定检索范围 |
| 4 | 更新状态偏好（追更 / 只看完本） | 决定候选池，常被忽略但影响极大 |
| 5 | 长度容忍度（百万字以上是否劝退） | 排除大量候选 |
| 6 | 明确说“绝对不看”的东西 | 硬雷点，优先级最高 |

### 3. 增量更新（收到新反馈时）

每次用户评价一本书后，做三件事，缺一不可：

1. 更新 `novel-reading-log` 里该书的 `status` / `rating` / `drop_reason`。
2. 把反馈**抽象成偏好**，追加或调整权重到 `preference-profile.yaml`，写明 `evidence`。
3. 若新证据与旧偏好冲突（例如档案写“爱看慢热”，但新反馈嫌弃节奏慢），**不要静默覆盖**：把冲突摆出来让用户裁决，再改。

### 4. 版本管理

- 每次实质修改在 `changelog` 追加一行：日期、改了什么、依据什么证据。
- 不要删除旧偏好，改为调整权重或标 `deprecated: true`，保留演化轨迹，便于回溯“为什么系统后来变了口味”。

## 输出要求

建档或更新完成后，向用户回报一份**不超过 20 行**的摘要：

- 已确认的强偏好（weight ≥ 4）
- 硬雷点清单
- 不确定项（`confidence: low`）与需要用户确认的问题
- 档案文件路径

不要输出整个 YAML 全文，用户不需要看原始文件。

## 反面清单（不要做）

- 不要把用户随口一句话当成决定性偏好（“最近有点想看仙侠” ≠ 仙侠是强偏好）。
- 不要用“热门/经典”这类无信息量标签填充档案。
- 不要在没读过档案的情况下开始推荐（这是最常见的失败模式）。
- 不要为了显得周全而把所有维度都问一遍，过度提问会消耗用户耐心。
